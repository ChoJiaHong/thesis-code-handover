# 實驗腳本操作手冊

## `experiment_ctrl_v2.py`：主要實驗控制器（三種情境）

```bash
python3 experiment_ctrl_v2.py --scenario <1|2|3> --url http://<controller-ip>:<port> \
  [--fail-node pdclab] [--seed 42] [--profile user_profiles.json] [--no-status]
```

- `--scenario`：1/2/3三選一（**必填**）。腳本檔頭範例：
  `python experiment_ctrl_v2.py --scenario 3 --url http://10.52.52.111:30004 --fail-node pdclab`
- `--fail-node`：`--scenario 3`時觸發節點故障之目標節點名稱，預設`pdclab`。腳本內部
  `scenario_node_failure()`會呼叫`node_failure(url, fail_node)`直接對Controller
  的`/alert`端點送出故障事件（屬邏輯層模擬，並非真的切斷網路）
- 輸出：`results/<solver_mode>/s<scenario>_<時間戳>.csv`（`solver_mode`由查詢
  Controller的`/status`取得）

### scenario編號與論文三個實驗情境的對應關係（2026-09-03確認）

程式碼中`--scenario`直接決定輸出檔名前綴（`s1`/`s2`/`s3`），但論文「實驗二：高負載情境」
與「實驗三：節點故障情境」的最終資料**檔名前綴皆為`s2_`**，並非分別對應`--scenario 2`與
`--scenario 3`——已確認：「節點故障情境」實際上是以`--scenario 2`（高負載設定）為基礎，
在其穩定運行期間另外執行`inject_node_failure.sh`（見本目錄）進行**真實網路層故障注入**，
而非本腳本內建的`--fail-node`邏輯模擬（該邏輯僅是對Controller的`/alert`端點直接送出
邏輯事件，並未真的斷網，故未採用）。

`inject_node_failure.sh`之實際做法：
1. 對三個目標節點，以`kubectl delete pods --field-selector spec.nodeName=<node>`
   立即清除該節點上所有Pod（強制服務中斷，不等待逾時）。
2. 透過`kubectl exec`進入各節點上的`kube-proxy` Pod（與宿主機共用network namespace），
   注入iptables規則封鎖：(a) TCP dport 30501之inbound、(b) 到控制平面IP之outbound，
   持續60秒後以`trap`確保還原（即使腳本中斷也會清除規則）。
3. 三節點平行執行（background + wait）。

此機制解釋了CSV中`node_status`欄位（Monitor透過Prometheus`kube_node_status_condition`
偵測到的節點健康狀態）為何是在事件發生後有延遲才轉為`unhealthy`——kubelet需等待
心跳逾時才會被Kubernetes標記為NotReady，而`kubectl delete pods`造成的服務中斷則是
立即發生，兩者存在時間差（見`docs/data_provenance.md`「更正：exp3資料夾先前收錄
錯誤批次」一節之實測時序）。

## `experiment_ctrl.py`：真實AR emulator子進程版

情境流程與`experiment_ctrl_v2.py`相同，差異在於改用子進程方式呼叫真正的
`ar_emulator/AR_emulator_nosub.py`（而非in-process模擬），需保證
`ar_emulator/1280hand.jpg`與`AR_emulator_nosub.py`同目錄。

## `bench_workability.py`：離線壓測腳本（產生服務容量表種子資料）

```bash
python3 bench_workability.py --node <節點名，對應serviceSpec_mul.json的key> \
  --host <節點IP> \
  [--gesture-port <埠>] [--pose-port <埠>] [--object-port <埠>] \
  [--duration 30] [--concurrency 20] [--send-interval 0.001]
```

**依賴（2026-09-03補上，先前版本缺這批檔案會直接ImportError無法執行）**：本腳本直接以
gRPC對推論服務壓測，需要`gesture_pb2.py`／`gesture_pb2_grpc.py`／`pose_pb2.py`／
`pose_pb2_grpc.py`（已從`agent/`複製一份至本目錄，與該處為同一份stub、非另行維護）；
另需安裝`requirements.txt`所列套件，注意`grpcio`版本需≥1.71.0（版本過舊import時會
直接丟RuntimeError）。

至少需指定一個服務埠。對每個服務組合進行gRPC壓測，計算穩定QPS，執行完會提示手動將
數值更新進`controller/information/serviceSpec_mul.json`（**非自動寫入**）。對應論文
4-1-2、4-1-10節、表5之\(W(i,c,j)\)量測方法。

## `rebuild_metrics_from_agent_logs.py`：用Agent端log重新校正實驗CSV

```bash
python3 rebuild_metrics_from_agent_logs.py \
  --csv <experiment_ctrl_v2.py輸出的原始CSV> \
  --agent-log-dir <Agent端log目錄，可多個> \
  --start-time <實驗起始時間> \
  --out <輸出之修正版CSV> \
  [--threshold <FPS門檻>] [--latency-ms <延遲門檻ms>]
```

用途：以Agent端（伺服器權威資料）重新計算experiment_ctrl_v2.py CSV中的指標，校正
可能因網路延遲等因素造成的記錄誤差。
